# Siparo backend: Render Free + Neon Free

Java 17 / Spring Boot runs on Render; PostgreSQL and private image storage run on Neon.
Use the existing `master` branch. No local database or uploaded files are migrated.

## Provision

1. Use the Neon Free project in AWS Frankfurt (`eu-central-1`). Reuse the existing project/branch/database if
   one exists. Create a **private** `siparo-images` object storage bucket on the same branch and storage
   credentials with read + write scope.
2. Connect only `yusufinann/siparo-backend` to Render. Deploy `render.yaml` as a Blueprint,
   or create a Docker Web Service with **Free**, **Frankfurt**, branch **master**,
   Dockerfile `./Dockerfile`, health path `/api/v1/public/health`.
3. Set the variables below in Render's Environment settings. Do not commit credentials.
4. Deploy and wait for Live. Check `/api/v1/public/health` returns `{"status":"UP"}`
   and `/api/v1/public/config` succeeds. The health endpoint is liveness-only;
   it intentionally does not query PostgreSQL on every Render probe.
5. Point mobile/web API URLs at the service's HTTPS URL. Add the actual web frontend
   origins to CORS. Mobile native clients do not require a CORS wildcard.

## Environment

| Variable | Value |
| --- | --- |
| `SPRING_PROFILES_ACTIVE` | `prod,render` |
| `DB_URL` | Neon **direct** (non-pooled) JDBC URL without credentials, `jdbc:postgresql://HOST/DATABASE?sslmode=require` |
| `DB_USERNAME`, `DB_PASSWORD` | Neon database role and password |
| `JWT_SECRET` | Independently generated random secret, at least 32 bytes |
| `DELIVERY_PIN_SECRET` | Separate random secret |
| `AUTH_RESET_SECRET` | Separate random secret, at least 32 characters |
| `CORS_ALLOWED_ORIGINS` | Comma-separated exact frontend origins, e.g. `https://siparo.app,https://isletme.siparo.app` |
| `AWS_ENDPOINT_URL_S3` | Neon branch storage endpoint, e.g. `https://BRANCH_ID.storage.c-N.eu-central-1.aws.neon.tech` |
| `AWS_REGION` | Region from Neon storage connection details (Frankfurt: `eu-central-1`) |
| `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` | Neon Storage credentials |
| `UPLOADS_S3_BUCKET` | `siparo-images` |

Blueprint generates the three application secrets automatically. For manual service
creation, generate them separately with a cryptographically secure generator.
Use direct DB connections for this single small JVM: Hikari limits connections to 5,
releases idle connections, and Flyway uses the same direct URL. Flyway runs V1–V24
automatically on the empty database. Never manually baseline this fresh database.

## Images

The `render` profile writes optimized images to Neon Object Storage (key `images/UUID.ext`).
The API contract is unchanged: uploads return `https://<backend>/uploads/UUID.ext`, and the backend
streams the bytes for that URL from the private bucket. Clients never receive storage credentials
or signed URLs. Only filenames generated by the upload service can be read; responses are cached
as immutable because every upload gets a new random name. The local development profile keeps
filesystem storage.
Do not switch hosted uploads back to local disk: Render Free discards it on restart.

## Free tier limits and unavailable integrations

- Render Free sleeps after 15 minutes without traffic; a cold start can take about a minute.
  This is suitable for a demo/pilot, not uninterrupted order processing.
- Render Free has monthly compute/bandwidth/build limits. Keep a $0 spend limit where
  available, do not enable paid compute or automatic upgrades.
- Neon Free currently includes 100 CU-hours, 0.5 GB PostgreSQL storage and 5 GB object
  storage per project; quotas and pricing can change. Monitor dashboard usage.
- Render Free blocks SMTP ports 25, 465, and 587. Email password reset remains unavailable
  unless you configure a provider that supports an allowed TLS/STARTTLS port (e.g. 2525),
  or add an HTTPS email provider. Do not copy the local SMTP settings blindly.
- Google login needs production client IDs. SMS, online payments and push notifications
  also require their respective provider configuration. Deployment does not enable them.
- Old local `/uploads/` URLs and existing local DB contents are not copied by this setup.

## Verification

`mvn -B -ntp package` compiles and runs unit tests. The PostgreSQL integration suite is
opt-in via `AUTH_TEST_DB_URL` pointing to an isolated test DB, never the live database; it also
proves that Flyway V1–V24 applies cleanly to an empty database. Docker runs the unit tests while
building, so a failing test blocks the Render deploy. Docker is not installed locally on this machine;
the actual Linux image must also build successfully on Render before deployment is verified.
